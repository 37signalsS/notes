# Политика доступа к ключам шифрования (Transit Engine)

## Определения

**Политика доступа к ключам шифрования** — это набор правил, которые определяют, кто (пользователь, приложение) и при каких условиях может создавать, использовать, ротировать и уничтожать криптографические ключи в Vault. Основная цель — реализовать принцип наименьших привилегий и разделение обязанностей для криптографических операций.

## Основные концепции

В Vault управление ключами и операциями шифрования чаще всего реализуется через движок секретов **`transit`**. Он предоставляет "шифрование как сервис" (encryption-as-a-service), не сохраняя данные, которые он шифрует.

### Принципы

*   **Минимально необходимый доступ:** Роли должны получать права только на те операции, которые им необходимы (например, `encrypt` и `decrypt`, но не `export` или `delete`).
*   **Разделение обязанностей:** Администраторы, управляющие жизненным циклом ключей, и приложения, использующие их, должны иметь разные роли и политики.
*   **Невозможность извлечения ключей:** Ключи в `transit` по умолчанию не могут быть извлечены (`exportable=false`). Это предотвращает утечку самого ключевого материала.
*   **Аудит:** Все криптографические операции должны протоколироваться для последующего анализа.

### Объекты и операции

Политики строятся вокруг путей API движка `transit`:

*   **Типы ключей:** `transit` поддерживает различные типы ключей для шифрования, подписи и HMAC.
*   **Операции:**
    *   `/transit/keys/<name>`: Управление ключом (создание, чтение метаданных, обновление).
    *   `/transit/encrypt/<name>`: Шифрование данных.
    *   `/transit/decrypt/<name>`: Расшифровка данных.
    *   `/transit/rewrap/<name>`: Перешифрование данных новой версией ключа без их расшифровки.
    *   `/transit/sign/<name>`: Создание цифровой подписи.
    *   `/transit/verify/<name>`: Проверка подписи.
    *   `/transit/keys/<name>/rotate`: Ротация ключа (создание новой версии).

## Практические сценарии

### Политика для приложения

Приложению, которому нужно шифровать и расшифровывать данные, выдается политика, разрешающая только эти операции для конкретного ключа.

*   **Имя ключа:** `payments`
*   **Задача:** Шифровать и расшифровывать номера карт.

```hcl
# Политика 'app-payments-policy.hcl'

# Разрешить шифрование с использованием ключа 'payments'
path "transit/encrypt/payments" {
  capabilities = ["update"] # 'update', так как это POST-запрос
}

# Разрешить расшифровку с использованием ключа 'payments'
path "transit/decrypt/payments" {
  capabilities = ["update"]
}

# Разрешить чтение метаданных ключа (не самого ключа)
path "transit/keys/payments" {
  capabilities = ["read"]
}
```
**Важно:** У этой роли нет прав на ротацию, удаление или изменение ключа.

### Политика для администратора ключей

Администратор может управлять ключами, но ему не обязательно иметь доступ к расшифровке данных.

*   **Задача:** Управлять жизненным циклом ключа `payments`.

```hcl
# Политика 'admin-payments-policy.hcl'

# Управление ключом (создание, чтение, обновление)
path "transit/keys/payments" {
  capabilities = ["create", "read", "update", "list"]
}

# Разрешить ротацию ключа
path "transit/keys/payments/rotate" {
  capabilities = ["update"]
}

# Явный запрет на расшифровку данных
path "transit/decrypt/payments" {
  capabilities = ["deny"]
}
```
Этот пример демонстрирует **разделение обязанностей**: приложение использует ключ, администратор им управляет.

### Безопасная доставка секрета через Response Wrapping

Чтобы безопасно передать зашифрованное значение или другой секрет, можно использовать `response wrapping`. Vault помещает ответ в одноразовый токен, который можно безопасно передать получателю.

```bash
# Зашифровать данные и обернуть ответ в токен с TTL 5 минут
vault write -wrap-ttl=5m transit/encrypt/payments 
  plaintext=$(echo -n "db-pass" | base64)

# Получатель использует wrapping-токен для получения результата
VAULT_TOKEN=<wrapping-token> vault unwrap
```
