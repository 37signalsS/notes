# Transit Encryption Policies

## Определения

**Политика доступа к ключам шифрования** — набор правил в Vault, определяющий, кто (пользователь, приложение) и какие криптографические операции может выполнять с помощью движка секретов [`transit`](../concepts.md#движки-секретов-secret-engines).

Цель — реализовать принцип наименьших привилегий и разделение обязанностей для "шифрования как сервиса" (encryption-as-a-service).

## Основные концепции

Движок `transit` позволяет приложениям шифровать и подписывать данные без прямого доступа к криптографическим ключам. Ключи хранятся в Vault и никогда его не покидают.

### Принципы построения политик для `transit`

* **Минимально необходимый доступ:** роли получают права только на необходимые операции (например, `encrypt`/`decrypt`, но не `export`/`delete`).
* **Разделение обязанностей:** администраторы жизненного цикла ключей и приложения-пользователи ключей имеют разные роли и политики.
* **Невозможность извлечения ключей:** ключи по умолчанию создаются как неизвлекаемые (`exportable=false`).
* **Аудит:** все криптографические операции протоколируются через [устройства аудита](../concepts.md#аудит-audit-devices).

### Пути и операции

Политики строятся вокруг путей API движка `transit`:

| Путь | Операция | Capabilities |
| :--- | :--- | :--- |
| `transit/keys/<name>` | Управление ключом | `create`, `read`, `update`, `list` |
| `transit/encrypt/<name>` | Шифрование данных | `update` |
| `transit/decrypt/<name>` | Расшифровка данных | `update` |
| `transit/rewrap/<name>` | Перешифрование новой версией ключа | `update` |
| `transit/sign/<name>` | Создание цифровой подписи | `update` |
| `transit/verify/<name>` | Проверка подписи | `update` |
| `transit/keys/<name>/rotate` | Ротация ключа | `update` |

Принципы Zero Trust, реализуемые Transit engine, описаны в [подходе Zero Trust к управлению секретами](../zero_trust.md).

## Практические сценарии

### Сценарий 1: Политика для приложения

Приложению, которому нужно шифровать и расшифровывать данные, выдаётся политика, разрешающая только эти операции для конкретного ключа.

**Имя ключа:** `payments`
**Задача:** шифровать и расшифровывать данные.

```hcl
# Политика 'app-payments-policy.hcl'

# Разрешить шифрование с использованием ключа 'payments'
path "transit/encrypt/payments" {
  capabilities = ["update"] # 'update' для POST-запросов
}

# Разрешить расшифровку с использованием ключа 'payments'
path "transit/decrypt/payments" {
  capabilities = ["update"]
}
```

**Результат:** роль не имеет прав на ротацию, удаление или изменение ключа.

### Сценарий 2: Политика для администратора ключей

Администратор управляет жизненным циклом ключей, но не имеет доступа к расшифровке конфиденциальных данных.

**Задача:** управление ключом `payments`.

```hcl
# Политика 'admin-payments-policy.hcl'

# Управление ключом (создание, чтение, обновление, листинг)
path "transit/keys/*" {
  capabilities = ["create", "read", "update", "list"]
}

# Разрешить ротацию ключа
path "transit/keys/payments/rotate" {
  capabilities = ["update"]
}

# Явный запрет на расшифровку данных
path "transit/decrypt/payments" {
  capabilities = ["deny"]
}
```

**Результат:** реализовано разделение обязанностей — администратор управляет ключами, но не может расшифровывать данные.

## Дополнительная информация

Для безопасной передачи зашифрованного значения используется механизм [Response Wrapping](../concepts.md#response-wrapping) — Vault помещает ответ в одноразовый токен, передаваемый получателю. Настройка доступа для приложений выполняется через [аутентификацию AppRole](./vault_auth_approle.md). Полное руководство по возможностям Transit engine доступно в [официальной документации HashiCorp](https://developer.hashicorp.com/vault/docs/secrets/transit).
