# Vault Agent Sidecar — динамическое обновление конфигурации

## Определения

**Vault Agent Sidecar** — это архитектурный паттерн использования `vault-agent` в качестве постоянно работающего вспомогательного контейнера в Kubernetes-поде. Он отвечает за аутентификацию, получение секретов и их динамическое обновление в конфигурационных файлах основного приложения без перезапуска пода.

**Динамическая ротация (Dynamic Rotation)** — процесс автоматического обновления секретов (например, паролей БД или сертификатов) в работающем приложении. Агент отслеживает изменения в Vault, перезаписывает файлы и отправляет сигнал приложению (обычно `SIGHUP`) для перечитывания конфигурации.

**Native Sidecar Containers (K8s 1.29+)** — механизм Kubernetes, позволяющий определять вспомогательные контейнеры в блоке `initContainers` с параметром `restartPolicy: Always`. Это гарантирует, что Vault Agent запустится раньше основного приложения и будет доступен на протяжении всего жизненного цикла пода.

## Основные концепции

### Механизмы взаимодействия контейнеров

В паттерне Sidecar агент и приложение должны обмениваться данными и сигналами.

1.  **Общий том (Shared Volume):** Используется `emptyDir` с типом `Memory` (tmpfs) для передачи секретов в виде файлов. Это исключает запись чувствительных данных на физический диск узла.
2.  **Сигнализация (Signaling):** Для отправки сигналов (например, `pkill -HUP`) между контейнерами используются следующие настройки:
    *   **`shareProcessNamespace: true`**: Позволяет процессам в разных контейнерах одного пода видеть друг друга в общем PID-пространстве.
    *   **`SYS_PTRACE` Capability**: Разрешает агенту отправлять сигналы процессам других контейнеров.
3.  **Идентификация пользователя (UID):** Для корректной работы сигналов и прав доступа к файлам рекомендуется запускать агента и приложение под одним `runAsUser`.

### Жизненный цикл с Native Sidecars

При использовании нативных сайдкаров (K8s 1.29+):
1.  Vault Agent запускается как `initContainer` с `restartPolicy: Always`.
2.  Агент проходит аутентификацию и рендерит секреты.
3.  Kubernetes переходит к запуску основного контейнера только после того, как агент станет `Ready`.
4.  При завершении пода агент выключается последним, обеспечивая доступность секретов до полной остановки приложения.

## Практические сценарии

### Сценарий 1: Настройка Vault Agent для Sidecar

Файл конфигурации агента (`agent-config.hcl`) должен настраивать автоматическую аутентификацию и команду перезагрузки.

```hcl
vault {
  address = "https://vault.example.com:8200"
}

auto_auth {
  method "kubernetes" {
    config = {
      role = "webapp-role"
    }
  }
}

cache {
  use_auto_auth_token = true
}

template {
  source      = "/vault/templates/db.ctmpl"
  destination = "/etc/app/config.yaml"
  
  # Отправка сигнала SIGHUP основному приложению (название процесса: myapp)
  command = "pkill -HUP myapp"
}
```

### Сценарий 2: Манифест Deployment с ручным Sidecar

Пример реализации через классический Sidecar (для версий K8s ниже 1.29 или специфичных требований).

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: webapp-sidecar
spec:
  replicas: 1
  template:
    spec:
      # Общее PID-пространство для отправки SIGHUP
      shareProcessNamespace: true
      serviceAccountName: webapp-sa
      volumes:
      - name: secrets-volume
        emptyDir: { medium: Memory }
      containers:
      - name: webapp
        image: my-app:latest
        volumeMounts:
        - name: secrets-volume
          mountPath: /etc/app
      - name: vault-agent
        image: hashicorp/vault:1.16
        securityContext:
          capabilities:
            add: ["SYS_PTRACE"] # Разрешение на отправку сигналов
        volumeMounts:
        - name: secrets-volume
          mountPath: /vault/secrets
        args: ["agent", "-config=/etc/vault/agent-config.hcl"]
```

### Сценарий 3: Использование Native Sidecar (K8s 1.29+)

Этот метод исключает race conditions при старте приложения.

```yaml
spec:
  initContainers:
  - name: vault-agent
    image: hashicorp/vault:1.16
    restartPolicy: Always # Делает контейнер нативным сайдкаром
    # ... конфигурация аналогична сценарию 2 ...
  containers:
  - name: webapp
    # ... приложение запустится только после готовности агента ...
```

## Дополнительная информация

### Преимущества и недостатки

| Характеристика | Преимущество | Недостаток |
| :--- | :--- | :--- |
| **Ротация** | Обновление без рестарта подов. | Требует поддержки `SIGHUP` приложением. |
| **Изоляция** | Секреты только в памяти (`tmpfs`). | `shareProcessNamespace` ослабляет изоляцию процессов. |
| **Универсальность** | Работает в любом K8s без инжектора. | Требует ручного описания YAML для каждого Deployment. |

### Рекомендации

1.  **Лимиты ресурсов:** Всегда указывайте `resources.limits` для сайдкара, чтобы он не влиял на стабильность основного приложения.
2.  **Persistent Cache:** Используйте BoltDB кэш в агенте для мгновенного восстановления токена при перезапуске контейнера агента.
3.  **Graceful Shutdown:** Настройте `terminationGracePeriodSeconds` (минимум 30 сек), чтобы агент успел корректно закрыть сессии.
