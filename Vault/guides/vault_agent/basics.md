# Vault Agent — определения и базовая конфигурация

## Определения

* **Vault Agent** — это режим работы бинарного файла `vault`, который позволяет реализовать несколько полезных паттернов для работы с секретами без необходимости встраивать логику Vault в код самого приложения. Он действует как посредник между приложением и сервером Vault.

### Ключевые задачи агента

1. **Автоматическая аутентификация:** Агент самостоятельно аутентифицируется в Vault (например, через метод [AppRole](../vault_auth_approle.md)), используя настроенный метод.
2. **Управление жизненным циклом токена:** Агент кэширует полученный токен и автоматически обновляет его по истечении срока действия.
3. **Рендеринг секретов в файлы:** Агент может запрашивать секреты из Vault и, используя встроенный шаблонизатор, записывать их в конфигурационные файлы приложения в нужном формате.
4. **Обновление без перезапуска:** Благодаря параметру `command` в блоке шаблона, агент может инициировать перезагрузку конфигурации приложения (например, через `SIGHUP` или вызов скрипта) сразу после обновления секрета. Это позволяет реализовать **бесшовную ротацию секретов** без простоя сервиса.

## Основные концепции

Агент управляется через отдельный конфигурационный файл в формате HCL.

```hcl
# /etc/vault.d/agent.hcl

# PID-файл для управления процессом
pid_file = "/var/run/vault-agent.pid"

# Указываем адрес Vault-сервера
vault {
  address = "http://127.0.0.1:8200"
}

# Блок автоматической аутентификации
auto_auth {
  method "approle" {
    config = {
      role_id_file_path = "/etc/vault.d/.role_id"
      secret_id_file_path = "/etc/vault.d/.secret_id"
    }
  }
}

# Блок шаблона для рендеринга секрета в файл
template {
  # Исходный файл-шаблон
  source      = "/etc/app/config.ctmpl"

  # Конечный файл, который будет сгенерирован
  destination = "/etc/app/config.json"

  # Опционально: команда, которая будет выполнена после успешного рендеринга
  # command = "systemctl reload my-app"
}
```

### Блок `auto_auth`

Этот блок настраивает автоматическую аутентификацию. В примере с `approle` агент будет читать `RoleID` и `SecretID` из указанных файлов. Это безопаснее, чем хранить их в самой конфигурации агента.

### Блок `template`

Этот блок описывает, как преобразовать шаблон в конечный файл.

* `source`: Путь к файлу-шаблону (`.ctmpl`).
* `destination`: Путь к итоговому файлу, который будет использовать ваше приложение.
* `command`: Позволяет уведомить приложение об обновлении конфигурации (например, отправив сигнал `SIGHUP` или выполнив команду перезагрузки).

### Синтаксис шаблонов

Шаблоны используют синтаксис, основанный на [Consul Template](https://github.com/hashicorp/consul-template). Для получения секрета из K/V-хранилища используется конструкция `with secret`:

```go-template
# /etc/app/config.ctmpl

# Запрашиваем секрет по пути devops/data/consul
{{ with secret "devops/data/consul" }}

# Обращаемся к данным внутри секрета
# Для KVv2 данные лежат внутри .Data.data
# Для KVv1 - внутри .Data
consul_token = "{{ .Data.data.token }}"

{{ end }}
```

1. `with secret "devops/data/consul"`: Агент запрашивает секрет по этому пути.
2. `.Data.data.token`: Мы получаем доступ к полю `token` внутри данных секрета.

## Практические сценарии

### Запуск агента

Агент запускается с указанием файла конфигурации:

```bash
vault agent -config=/etc/vault.d/agent.hcl
```

Для production-окружений рекомендуется запускать агента как `systemd` сервис, аналогично самому [Vault Server](../vault_installation.md).

### Сценарий: Ротация секретов без простоя

Для обеспечения безопасности межсервисного взаимодействия рекомендуется регулярно менять API-ключи. Vault Agent позволяет автоматизировать этот процесс:

1. **Обновление в Vault:** Администратор или автоматизированный скрипт обновляет секрет по пути `secret/data/webapp/api-key`.
2. **Обнаружение агентом:** Vault Agent, работающий как sidecar или отдельный демон, обнаруживает изменение секрета.
3. **Рендеринг:** Агент обновляет файл `/etc/app/config.json`, подставляя новое значение ключа.
4. **Уведомление:** Выполняется команда `command = "systemctl reload webapp"`.
5. **Результат:** Приложение перечитывает конфигурацию и начинает использовать новый ключ без прерывания обработки запросов.

### Пример: получение токена Consul

Рассмотрим сценарий, где агент должен получить токен для Consul и записать его в файл.

**1. Подготовка файлов `role_id` и `secret_id`**

```bash
# Получаем RoleID и записываем в файл
vault read -field=role_id auth/approle/role/ansible > /etc/vault.d/.role_id

# Получаем SecretID и записываем в файл
vault write -f -field=secret_id auth/approle/role/ansible > /etc/vault.d/.secret_id

# Устанавливаем права доступа
sudo chown vault:vault /etc/vault.d/.role_id /etc/vault.d/.secret_id
sudo chmod 400 /etc/vault.d/.role_id /etc/vault.d/.secret_id
```

**2. Запуск и проверка**

```bash
sudo -u vault vault agent -config=/etc/vault.d/agent.hcl
cat /etc/app/config.json # → token = "a1b2-c3d4-e5f6"
```

### Отладка: permission denied

Если в логах агента появляется ошибка `permission denied` при попытке доступа к секрету, это обычно указывает на проблему в политике, привязанной к AppRole.

```text
# → [ERROR] (agent) template.server: template server received error: permission denied
```

**Решение:**

1. **Проверьте политику:** выполните `vault policy read <policy_name>` и убедитесь в наличии прав `read`.
2. **Проверьте путь:** для K/V v2 хранилища API-путь всегда должен содержать `data` (например, `path "devops/data/consul"`).
3. **Соответствие путей:** убедитесь, что путь в политике точно соответствует пути в шаблоне.

## Дополнительная информация

### Блок `sink`

Позволяет переопределить место записи полученного токена (по умолчанию `~/.vault-token`):

```hcl
sink "file" {
  config = {
    path = "/etc/vault.d/.vault-token"
  }
}
```

### Блок `cache`

Снижает нагрузку на Vault-сервер, сохраняя прочитанные секреты в памяти агента.

```hcl
cache {
  use_auto_auth_token = true
}
```

**Важно:** кэш хранит секреты в памяти — при компрометации хоста злоумышленник может получить к ним доступ.

### Режим `exit_after_auth`

Заставляет агента завершиться сразу после успешной аутентификации. Полезно для CI/CD-пайплайнов.

```hcl
auto_auth {
  exit_after_auth = true
  # ... конфигурация метода ...
}
```

### Блок `listener` (режим прокси)

Агент может работать как HTTP-прокси, автоматически подставляя токен в запросы приложений:

```hcl
listener "tcp" {
  address = "127.0.0.1:8100"
  tls_disable = true
}
```

### Логирование

```hcl
log_level = "info" # trace, debug, info, warn, error
log_file = "/var/log/vault-agent.log"
```

### Сравнение подходов

| Сценарий | Конфигурация | Подробности |
| :--- | :--- | :--- |
| **Автономный агент** | `auto_auth` + `template` + `sink` | Текущий файл |
| **Sidecar в Kubernetes** | `auto_auth` + `template` + `command` | [Sidecar-паттерн](./sidecar_pattern.md) |
| **Auto-injection в Kubernetes** | Аннотации пода | [Vault Injector](./injector.md) |
