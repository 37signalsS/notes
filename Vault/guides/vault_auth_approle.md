# Аутентификация в Vault через AppRole

## Определения

**AppRole** — метод аутентификации (проверки подлинности) в **[HashiCorp Vault](../overview.md)**, специально разработанный для использования машинами и приложениями. Он позволяет сервисам получать доступ к секретам без участия человека, используя механизм, аналогичный паре "логин/пароль", но с расширенными возможностями контроля и безопасности.

Методы аутентификации в целом описаны в разделе **[Основные концепции](../concepts.md#методы-аутентификации-и-токены)**.

## Основные концепции

Работа метода AppRole строится на использовании двух ключевых идентификаторов:

* **RoleID (Идентификатор роли):** Аналог "логина". Обычно это статическое значение, привязанное к конкретному приложению или сервису. Сам по себе `RoleID` не является секретом, но его следует защищать от массового раскрытия.
* **SecretID (Секретный идентификатор):** Аналог "пароля". Это конфиденциальное значение, которое должно доставляться приложению через безопасные каналы.

При успешном предоставлении обеих частей (`RoleID` и `SecretID`) Vault выдает приложению временный токен, к которому привязаны соответствующие **[политики доступа](../authorization.md)**.

### Параметры безопасности роли

При настройке роли в AppRole доступны параметры для тонкого управления безопасностью:

| Параметр | Описание | Рекомендация |
| :--- | :--- | :--- |
| `bind_secret_id` | Обязательность предоставления `SecretID` для логина | `true` (рекомендуется для большинства сценариев) |
| `secret_id_bound_cidrs` | Список IP-адресов/подсетей, с которых разрешено создавать `SecretID` | Ограничить доверенными сетями управления или CI/CD (Continuous Integration / Continuous Deployment) |
| `token_bound_cidrs` | Список IP-адресов/подсетей, с которых разрешено использовать выданный токен | **Обязательно** ограничить сегментом сети, где запущено приложение |
| `secret_id_num_uses` | Максимальное количество использований одного `SecretID` | Установить в `1` для одноразовых процессов развертывания |
| `secret_id_ttl` | Время жизни `SecretID` (Time to Live) | Устанавливать минимально необходимое время (например, 24 часа) |
| `token_ttl` | Время жизни выдаваемого токена | Использовать короткие значения (например, 1 час) |

### Механизмы защиты: CIDR и работа без SecretID

1. **Ограничение по подсетям (Bound CIDRs):** Привязка `RoleID` и `SecretID` к конкретным IP-адресам (например, раннеров CI/CD) гарантирует, что даже в случае кражи данных злоумышленник не сможет ими воспользоваться извне разрешенной сети. **CIDR (Classless Inter-Domain Routing)** — метод бесклассовой адресации в сетях IP.
2. **Режим без SecretID (`bind_secret_id: false`):** Позволяет аутентификацию только по `RoleID`. Этот режим считается **крайне небезопасным** и допустим только при строжайшем ограничении через `token_bound_cidrs` в полностью доверенной изолированной сети.

## Практические сценарии

### Включение и базовая настройка

Для использования AppRole необходимо сначала активировать этот метод аутентификации:

```bash
# Через интерфейс командной строки (CLI)
vault auth enable approle
```

*В интерфейсе пользователя (UI) это выполняется в разделе `Access` -> `Authentication Methods` -> `Enable new method`.*

### Пример: Доступ приложения к секретам Consul

Сценарий: приложению необходимо получить токен для **[Consul](../../Consul/consul_overview.md)**, хранящийся в Vault.

#### 1. Подготовка секрета и политики

```bash
# Включение хранилища K/V (Key-Value) версии 2
vault secrets enable -path=devops kv-v2

# Запись секрета
vault kv put devops/consul token="a1b2-c3d4-e5f6"
```

Создайте файл политики `consul-read-policy.hcl`:

```hcl
path "devops/data/consul" {
  capabilities = ["read", "list"]
}
```

```bash
# Загрузка политики в Vault
vault policy write consul-read-policy consul-read-policy.hcl
```

#### 2. Создание и настройка роли

Создаем роль `app-runner`, привязывая к ней созданную политику:

```bash
# Запись конфигурации роли
vault write auth/approle/role/app-runner \
    token_policies="consul-read-policy" \
    token_ttl="1h" \
    token_max_ttl="4h"
```

#### 3. Получение идентификаторов для приложения

Эти шаги обычно выполняются инструментами автоматизации (Terraform, CI/CD-пайплайны):

```bash
# Получение RoleID
vault read auth/approle/role/app-runner/role-id

# Генерация нового SecretID
vault write -f auth/approle/role/app-runner/secret-id
```

### Процесс аутентификации приложения

Приложение (самостоятельно или через **[Vault Agent](./vault_agent/basics.md)**) выполняет вход:

```bash
vault write auth/approle/login \
    role_id="<ROLE_ID>" \
    secret_id="<SECRET_ID>"
```

В ответ Vault возвращает токен, который приложение использует в заголовке `X-Vault-Token` для всех последующих запросов к API.

## Дополнительная информация

`SecretID` является чувствительной информацией и никогда не должен храниться в открытом виде (в коде или системах контроля версий). Для его безопасной доставки рекомендуется использовать:

* Переменные окружения в защищенных средах.
* Облачные сервисы управления ключами (KMS).
* Встроенные механизмы секретов CI/CD систем.
* Автоматизацию через **[Vault Agent](./vault_agent/basics.md)**.
