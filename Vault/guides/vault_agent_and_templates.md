# Vault Agent и Шаблоны

## Определения

* **Vault Agent** — это режим работы бинарного файла `vault`, который позволяет реализовать несколько полезных паттернов для работы с секретами без необходимости встраивать логику Vault в код самого приложения. Он действует как посредник между приложением и сервером Vault.

Ключевые задачи агента:

1. **Автоматическая аутентификация:** Агент самостоятельно аутентифицируется в Vault (например, через метод [AppRole](./vault_auth_approle.md)), используя настроенный метод.
2. **Управление жизненным циклом токена:** Агент кэширует полученный токен и автоматически обновляет его по истечении срока действия.
3. **Рендеринг секретов в файлы:** Агент может запрашивать секреты из Vault и, используя встроенный шаблонизатор, записывать их в конфигурационные файлы приложения в нужном формате.

## Основные концепции

Агент управляется через отдельный конфигурационный файл в формате HCL.

```hcl
# /etc/vault.d/agent.hcl

# PID-файл для управления процессом
pid_file = "/var/run/vault-agent.pid"

# Указываем адрес Vault-сервера
vault {
  address = "http://127.0.0.1:8200"
}

# Блок автоматической аутентификации
auto_auth {
  method "approle" {
    config = {
      role_id_file_path = "/etc/vault.d/.role_id"
      secret_id_file_path = "/etc/vault.d/.secret_id"
    }
  }
}

# Блок шаблона для рендеринга секрета в файл
template {
  # Исходный файл-шаблон
  source      = "/etc/app/config.ctmpl"

  # Конечный файл, который будет сгенерирован
  destination = "/etc/app/config.json"

  # Опционально: команда, которая будет выполнена после успешного рендеринга
  # command = "systemctl reload my-app"
}
```

### Блок `auto_auth`

Этот блок настраивает автоматическую аутентификацию. В примере с `approle` агент будет читать `RoleID` и `SecretID` из указанных файлов. Это безопаснее, чем хранить их в самой конфигурации агента.

### Блок `template`

Этот блок описывает, как преобразовать шаблон в конечный файл.

* `source`: Путь к файлу-шаблону (`.ctmpl`).
* `destination`: Путь к итоговому файлу, который будет использовать ваше приложение.
* `command`: Позволяет уведомить приложение об обновлении конфигурации (например, отправив сигнал `SIGHUP` или выполнив команду перезагрузки).

### Синтаксис шаблонов

Шаблоны используют синтаксис, основанный на [Consul Template](https://github.com/hashicorp/consul-template).

Для получения секрета из K/V-хранилища используется конструкция `with secret`:

```go-template
# /etc/app/config.ctmpl

# Запрашиваем секрет по пути devops/data/consul
{{ with secret "devops/data/consul" }}

# Обращаемся к данным внутри секрета
# Для KVv2 данные лежат внутри .Data.data
# Для KVv1 - внутри .Data
consul_token = "{{ .Data.data.token }}"

{{ end }}
```

В данном примере:

1. `with secret "devops/data/consul"`: Агент запрашивает секрет по этому пути.
2. `.Data.data.token`: Мы получаем доступ к полю `token` внутри данных секрета.

## Практические сценарии

### Запуск агента

Агент запускается с указанием файла конфигурации:

```bash
vault agent -config=/etc/vault.d/agent.hcl
```

Для production-окружений рекомендуется запускать агента как `systemd` сервис, аналогично самому [Vault](./vault_installation.md).

### Пример: получение токена Consul

Рассмотрим сценарий, где агент должен получить токен для [Consul](../../Consul/consul_overview.md) и записать его в файл.

**1. Файлы `role_id` и `secret_id`**
Сначала необходимо получить `RoleID` и `SecretID` для вашей [AppRole](./vault_auth_approle.md) и записать их в файлы, указанные в конфигурации агента.

```bash
# Получаем RoleID и записываем в файл
vault read -field=role_id auth/approle/role/ansible > /etc/vault.d/.role_id

# Получаем SecretID и записываем в файл
vault write -f -field=secret_id auth/approle/role/ansible > /etc/vault.d/.secret_id

# Устанавливаем права, чтобы только Vault мог их читать
sudo chown vault:vault /etc/vault.d/.role_id /etc/vault.d/.secret_id
sudo chmod 400 /etc/vault.d/.role_id /etc/vault.d/.secret_id
```

**2. Запуск и проверка**
Запускаем агента от имени пользователя `vault` и проверяем результат.

```bash
sudo -u vault vault agent -config=/etc/vault.d/agent.hcl

# Проверяем результат
cat /etc/app/config.json
```

```
token = "a1b2-c3d4-e5f6"
```

## Сценарий: Динамическое обновление конфигурации в Kubernetes

В Kubernetes стандартный способ обновления конфигурации приложения — это перезапуск пода. Инструменты, такие как `Reloader`, отслеживают изменения в `ConfigMap` или `Secret` и автоматически выполняют rolling update для `Deployment`. Однако этот подход не работает, когда секреты доставляются напрямую из Vault (например, через CSI-драйвер), так как Kubernetes-ресурсы не меняются.

Для приложений, требующих обновления конфигурации "на лету" без перезапуска, можно использовать паттерн с **`vault-agent` в режиме `sidecar`-контейнера**, который отправляет сигнал `SIGHUP` основному процессу.

### Структура пода

Под будет состоять из трех контейнеров:

1. **`initContainer` (`vault-agent`)**: Однократно запускается при старте пода, генерирует первоначальную версию конфигурационного файла из шаблона и секретов, после чего завершает работу.
2. **Основной контейнер приложения** (например, `nginx`): Использует сгенерированный конфигурационный файл.
3. **`sidecar`-контейнер (`vault-agent`)**: Работает постоянно. Периодически проверяет изменения в секретах Vault. При обнаружении изменений он заново рендерит конфигурационный файл и отправляет сигнал `SIGHUP` процессу в основном контейнере для перечитывания конфигурации.

### Настройка манифеста Kubernetes

Чтобы разрешить `sidecar`-контейнеру отправлять сигналы процессу в другом контейнере, необходимо ослабить изоляцию между ними. Это делается с компромиссом в безопасности.

```yaml
# Фрагмент Deployment.yaml
spec:
  template:
    spec:
      # 1. Общее пространство имен процессов
      shareProcessNamespace: true
      containers:
        - name: application
          image: nginx:latest
          # ...
        - name: vault-agent-sidecar
          image: vault:latest
          # ...
          # 2. Добавление capability для отправки сигналов
          securityContext:
            capabilities:
              add: ["SYS_PTRACE"]
```

#### 1. `shareProcessNamespace: true`

Этот параметр объединяет PID-namespace для всех контейнеров в поде.

**Последствия для безопасности:**

* **Нет PID 1**: Основной процесс в контейнере больше не имеет PID 1. Это может нарушить работу приложений, которые ожидают быть `init`-процессом.
* **Видимость процессов**: Процессы из одного контейнера видны процессам в других контейнерах (например, через команду `ps` или файловую систему `/proc`).
* **Доступ к файловой системе**: Через `/proc/{pid}/root` один контейнер может получить доступ к файловой системе другого.

#### 2. `securityContext.capabilities.add: ["SYS_PTRACE"]`

Эта Linux capability необходима, чтобы разрешить процессу (vault-agent) отправлять сигналы другим процессам, которые ему не принадлежат.

#### 3. Единый пользователь (`runAsUser`)

Для отправки сигналов между процессами без прав `root` необходимо, чтобы они выполнялись под одним и тем же пользователем (UID). Если основной процесс приложения работает от пользователя `nginx` (UID 101), то и `vault-agent` должен быть запущен с `runAsUser: 101`.

### Конфигурация Vault Agent для Sidecar

Конфигурация для `sidecar`-агента похожа на базовую, но с ключевым дополнением — `command` в блоке `template`.

```hcl
# vault-agent-sidecar-config.hcl

vault {
  address = "http://vault.vault.svc:8200"
}

auto_auth {
  method "kubernetes" {
    mount_path = "auth/kubernetes"
    config = {
      role = "my-app-role"
    }
  }
}

# exit_after_auth = false (по умолчанию), агент продолжает работать

template {
  source      = "/vault/configs/nginx.ctmpl"
  destination = "/usr/share/nginx/html/index.html"
  
  # Команда для поиска PID nginx и отправки SIGHUP
  # pkill отправляет сигнал всем процессам с именем 'nginx'
  command = "pkill -HUP nginx"
}
```

* **`exit_after_auth: false`**: Агент не завершает работу и продолжает следить за секретами.
* **`command = "pkill -HUP nginx"`**: После каждого успешного обновления файла `index.html` `vault-agent` выполнит команду `pkill`. Она найдет все процессы с именем `nginx` в общем PID-namespace и отправит им сигнал `SIGHUP`, заставляя перечитать конфигурацию. Это более надежно, чем поиск конкретного PID, который может меняться.

Этот подход создает мощный механизм для динамического управления конфигурациями, но требует тщательной оценки рисков безопасности из-за ослабления изоляции контейнеров.

## Дополнительная информация

### Отладка: `permission denied`

Если вы видите в логах агента ошибку `permission denied` при попытке доступа к секрету, скорее всего, проблема в политике, привязанной к AppRole.

```
[ERROR] (agent) template.server: template server received error: permission denied
```

**Решение:**

1. **Проверьте политику:** Зайдите в UI Vault или выполните `vault policy read <policy_name>`.
2. **Проверьте путь:** Убедитесь, что путь в политике точно соответствует пути, который запрашивает агент. **Для K/V v2 хранилища API-путь всегда должен содержать `data`**.
    * **Неправильно:** `path "devops/consul"`
    * **Правильно:** `path "devops/data/consul"`
3. **Проверьте права (`capabilities`):** Убедитесь, что у политики есть право на `read`.

После исправления политики агент при следующей попытке должен успешно отрендерить шаблон.
