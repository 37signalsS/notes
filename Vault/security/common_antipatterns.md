# Типичные ошибки при хранении конфиденциальных данных

Проблемы с секретами возникают на всех этапах жизненного цикла: от локальной разработки и CI/CD до продакшена. Ошибки часто незаметны — они появляются в рутине коммитов, конфигураций, логирования и сборки образов.

## Частые антипаттерны

#### 1. Секреты в системе контроля версий (Git)
Самая частая и опасная ошибка. Разработчики коммитят файлы `.env`, `kubeconfig`, приватные ключи или токены API. Даже если файл потом удалить, **секрет навсегда остается в истории Git**.
*   **Как обнаружить:**
    ```bash
    # Поиск по содержимому коммитов
    git log -p -S 'AWS_SECRET_ACCESS_KEY'

    # Поиск по всей истории на наличие паттернов ключей
    git grep -nE '(AKIA[0-9A-Z]{16}|BEGIN RSA PRIVATE KEY)' $(git rev-list --all)
    ```

#### 2. Кодирование Base64 — это не шифрование
В Kubernetes Secrets и других системах данные часто кодируются в Base64. Это всего лишь представление бинарных данных в текстовом виде, а не защита.
*   **Как "расшифровать":**
    ```bash
    echo 'cGFzc3dvcmQxMjM=' | base64 -d
    # Вывод: password123
    ```
Хранение таких секретов в Git эквивалентно хранению в открытом виде.

#### 3. Секреты в переменных окружения
Переменные окружения могут быть легко прочитаны другими процессами на той же машине и часто утекают в логи или отчеты об ошибках.
*   **Как прочитать на Linux:**
    ```bash
    # /proc файловая система раскрывает окружение процесса
    cat /proc/$(pgrep -f myapp | head -1)/environ
    ```

#### 4. Логирование чувствительных данных
Приложения могут случайно или намеренно (в режиме отладки) выводить в stdout/stderr пароли, токены, заголовки `Authorization` или полные тела запросов. Эти логи затем агрегируются и хранятся длительное время.

#### 5. Секреты внутри слоев контейнерных образов
Если в `Dockerfile` сначала скопировать файл с ключом, а затем удалить его, он все равно останется в одном из слоев образа.
*   **Антипаттерн в `Dockerfile`:**
    ```dockerfile
    FROM alpine
    # ПЛОХО: ключ копируется в слой
    COPY id_rsa /root/.ssh/id_rsa
    RUN ...
    # ПЛОХО: rm создает новый слой, но старый слой с ключом остается
    RUN rm /root/.ssh/id_rsa
    ```
*   **Как обнаружить:**
    ```bash
    # Проанализировать историю слоев
    docker history --no-trunc my-image:latest
    ```
    Для безопасной передачи build-time секретов следует использовать `RUN --mount=type=secret,...`.

#### 6. Избыточные права доступа (IAM/RBAC)
Создание "широких" политик (например, `secrets:GetSecretValue` для `Resource: "*"`) или использование одного сервисного аккаунта для нескольких приложений упрощает латеральное перемещение атакующего по системе в случае компрометации одного из компонентов.

#### 7. Утечки в CI/CD
Секреты часто хранятся в переменных окружения CI/CD систем и могут утечь через:
*   Логи выполнения задач (если не замаскированы).
*   Артефакты сборки.
*   Общий кэш.

#### 8. Секреты в файлах состояния IaC
Инструменты вроде Terraform хранят состояние инфраструктуры, включая значения секретов, в файлах `terraform.tfstate`. Эти файлы часто попадают в общие хранилища (S3 buckets) с неверно настроенными правами.

## Последствия и профилактика

| Ошибка | Риск | Профилактика |
| :--- | :--- | :--- |
| **Коммит секретов в Git** | Неотменяемая утечка через форки и клоны. | Pre-commit хуки (truffleHog, git-secrets), сканирование репозиториев, обучение. |
| **Base64 в K8s Secret** | Чтение любым, у кого есть `get` на `Secret`. | Шифрование etcd, использование [Sealed Secrets](. /../../Kubernetes/Security/sealed_secrets_overview.md) или внешних провайдеров. |
| **Секреты в слоях образа** | Массовая компрометация при публикации образа. | Многостадийная сборка, `RUN --mount=type=secret`, сканеры образов. |
| **Избыточные права** | Латеральное перемещение, эскалация привилегий. | Принцип наименьших привилегий, аудит прав, уникальные роли для каждого сервиса. |
| **Логи с секретами** | Утечка через системы сбора логов. | Маскирование на уровне логгера, санитайзеры в конвейере логов. |
