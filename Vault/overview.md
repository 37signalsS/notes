# Обзор HashiCorp Vault

## Определения

**HashiCorp Vault** — это централизованная система для безопасного управления жизненным циклом секретов (Security Lifecycle Management, SLM). Она предназначена для защиты чувствительных данных, таких как пароли, API-ключи, токены, сертификаты и ключи шифрования. Vault предоставляет единую точку управления для всей инфраструктуры, обеспечивая строгую идентификацию, гранулярную авторизацию и детальный аудит всех операций.

**Security Lifecycle Management (SLM)** — современный подход Vault (версии 1.16+, 2.0+), выходящий за рамки простого хранения секретов. SLM включает в себя обнаружение утечек в коде (Vault Radar), централизованное хранение, автоматическую ротацию и синхронизацию секретов с внешними облачными менеджерами ключей. Vault выступает центральным хранилищем (system of record) для чувствительных данных: паролей, сертификатов, ключей и токенов, а также идентификаций машин и людей, работающих с ними.

## Проблема: Secret Sprawl (Расползание секретов)

Основная задача Vault — решение проблемы **Secret Sprawl** (неконтролируемое распространение секретов), когда чувствительные данные оказываются рассредоточены по всей инфраструктуре:
*   **Локальные машины инженеров:** AWS-ключи, SSH-ключи, файлы конфигурации Kubernetes (`kubeconfig`).
*   **Системы документации:** Plain-text пароли на страницах Confluence или в общих файлах (Keepass).
*   **CI/CD переменные:** Учетные данные Docker Registry, AWS и SSH-ключи в настройках GitLab CI или Jenkins.
*   **Исходный код и Git:** API-ключи (Stripe, Facebook, Google) и учетные данные БД, жестко прописанные (hardcoded) в коде или конфигурационных файлах, попадающие в историю коммитов.

### Последствия Secret Sprawl
1.  **Отсутствие видимости:** Невозможно узнать, у кого есть доступ к конкретным учетным данным и где они используются.
2.  **Отсутствие аудита:** Нет возможности отследить, кто и когда использовал секрет. При компрометации невозможно определить источник утечки.
3.  **Сложность ротации:** Замена скомпрометированного ключа превращается в катастрофу, так как нужно вручную обновить его во всех разрозненных системах.

## Основные концепции

Архитектура Vault построена на принципах безопасности "Zero Trust" (нулевого доверия) и включает следующие фундаментальные механизмы:

*   **Брокер секретов (Secret Broker):** Vault выступает доверенным посредником между клиентами (людьми, сервисами) и целевыми системами (БД, облака), выдавая временные права доступа.
*   **[Процесс Seal/Unseal (Запечатывание)](./concepts.md#процесс-запечатывания-seal-и-распечатывания-unseal):** Механизм защиты главного ключа шифрования. В продуктивных средах рекомендуется использовать **Auto-unseal** через облачные KMS или HSM.
*   **[Интегрированное хранилище (Raft)](./concepts.md#бэкенды-хранения-storage-backends):** Современный стандарт хранения данных Vault, обеспечивающий высокую доступность (HA) без внешних зависимостей.
*   **[Система идентификации (Identity Store)](./concepts.md#система-идентификации-identity-store):** Механизм Entities и Groups, позволяющий связывать различные методы аутентификации с одной личностью.
*   **[Авторизация и политики (Policies)](./authorization.md):** Управление доступом на основе путей API с использованием декларативного языка HCL.
*   **[Движки секретов (Secret Engines)](./concepts.md#движки-секретов-secret-engines):** Компоненты, реализующие логику работы с данными: от статического KV до динамической генерации учетных данных баз данных и облаков.
*   **[Жизненный цикл (Lease & Revoke)](./concepts.md#жизненный-цикл-токены-lease-и-revoke):** Система аренды секретов с ограниченным временем жизни (TTL), обеспечивающая автоматический отзыв доступа.

### Ключевые преимущества

1.  **Централизация (Централизованное хранилище):** Исключение разрозненного хранения секретов в коде, конфигурациях и переменных окружения. Vault решает проблему **Secret Sprawl**, собирая все ключи и пароли в единую защищенную точку.
2.  **Многослойная защита (Layered Security):** Реализация принципа «луковицы», где безопасность обеспечивается не одной стеной, а множеством слоев: шифрование при хранении (at rest), шифрование при передаче (in transit), гранулярный доступ (ACL) и динамические токены.
3.  **Динамическая безопасность:** Генерация краткоживущих секретов "на лету" минимизирует ущерб при их компрометации и окно атаки (hacking window). Если секрет попадет в логи, он будет недействителен к моменту обнаружения злоумышленником.
4.  **Автоматизация ротации:** Встроенные механизмы обновления паролей и ключей без участия человека.
5.  **Синхронизация секретов (Secrets Sync):** Возможность управлять секретами в Vault и автоматически реплицировать их во внешние системы (destinations): AWS Secrets Manager, Google Cloud Secret Manager, Azure Key Vault, GitHub Actions/Repository Secrets и Vercel. Изменение секрета в Vault распространяется на целевые платформы в реальном времени. Доступно в Vault Enterprise и HCP Vault (Dedicated/Standard).

### Ключевые возможности

| Категория | Возможности |
| :--- | :--- |
| **Управление секретами** | Статическое хранение (KV v1/v2), динамические учетные данные (DB, Cloud, SSH). |
| **Криптография** | Шифрование как сервис (Transit Engine), маскирование данных, управление ключами (KMIP). |
| **Идентификация** | Поддержка OIDC, Workload Identity Federation (WIF), интеграция с LDAP/Okta/Active Directory. |
| **Синхронизация и Обнаружение** | Secrets Sync (Hub-and-spoke модель), Vault Radar (поиск секретов в коде и Slack). |
| **PKI и Сертификаты** | Полноценный центр сертификации (CA), поддержка ACME, выдача TLS и SSH сертификатов. |
| **Комплаенс и Аудит** | Неизменяемые логи, хэширование чувствительных данных в журналах, поддержка FIPS 140-2. |

## Практические сценарии

### Запуск в режиме разработки (Dev Mode)

Для быстрого ознакомления и тестирования Vault можно запустить в dev-режиме, не требующем настройки хранилища и распечатывания. Сервер стартует автоматически инициализированным и распечатанным: хранилище — `inmem` (в оперативной памяти), unseal-ключ и корневой токен выводятся в stdout при старте и теряются при остановке сервера.

```bash
# Запуск сервера в dev-режиме с известным корневым токеном (иначе генерируется случайный)
vault server -dev -dev-root-token-id='root'
# → WARNING! dev mode is enabled!
#   ... (вывод настройки прошивки сервера)
#   Root Token: root
#   Unseal Key: <unseal-ключ для dev-режима>

# Настройка CLI для работы с локальным сервером (выполняется в новом терминале)
export VAULT_ADDR='http://127.0.0.1:8200'
export VAULT_TOKEN='root' # Корневой токен из вывода предыдущей команды

# Проверка статуса
vault status
# → Key             Value
#   Seal Type       shamir
#   Initialized     true
#   Sealed          false
#   Storage Type    inmem
#   HA Enabled      false
```

Перед запуском в продакшн следует выбрать способ развертывания и источник хранилища (backend). Подробности по каждому варианту — в соответствующих руководствах:

| Сценарий | Хранилище | Способ | Руководство |
| :--- | :--- | :--- | :--- |
| Быстрый старт / dev | `inmem` | Dev Mode | см. выше |
| Одиночный сервер / продакшн | Raft (Integrated Storage) | Open Source / Enterprise | [Установка Vault](./guides/vault_installation.md) |
| Контейнерная среда | Raft | Docker / Docker Compose | [Vault в Docker](./guides/vault_docker_integration.md) |
| HA-кластер в Kubernetes | Raft | Helm / VSO / Agent Injector | [Интеграция с Kubernetes](./guides/vault_kubernetes_integration.md) |
| Управляемый сервис | HCP Vault | Enterprise (SaaS) | [Официальная документация](https://developer.hashicorp.com/vault/docs) |

Для HA-кластеров на Raft в Enterprise доступно **Snapshot Agent** (автоматическое резервное копирование снапшотом в облачные объектные хранилища), а для legacy-инсталляций — External Storage (Consul/Consul-кластер) как альтернативный backend.

### Примеры использования в инфраструктуре

*   **CI/CD интеграция:** Динамическая выдача временных токенов для пайплайнов GitLab/GitHub, исключающая хранение статических паролей в настройках CI.
*   **Kubernetes Sidecar:** Автоматическое внедрение секретов в поды через Vault Agent Sidecar или Secrets Store CSI Driver.
*   **Database Credentials:** Генерация уникальных логинов для каждого экземпляра микросервиса с автоматическим удалением пользователя в БД после истечения TTL.
*   **Zero Trust Networking:** Выдача краткоживущих TLS-сертификатов для взаимодействия между сервисами.
